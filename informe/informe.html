1. Introducción y estructura del repositorio

En este laboratorio se ejecutó el proyecto UNA Chat (Node.js, Express y Socket.IO), se comprobó que era vulnerable a la inyección de scripts (XSS) y se corrigió la validación de mensajes en la librería una-lib. Además, se agregó la funcionalidad para mostrar imágenes y videos a partir de URLs. El trabajo se verificó con tres tipos de pruebas automatizadas: unitarias, de integración y end-to-end.

Todo el código está en el repositorio https://github.com/Veldor09/lab5SI, organizado así:

2. Ejecución del proyecto y prueba de inyección de scripts (pasos 1 a 3)

Se instalaron las dependencias con npm install y se inició la aplicación original con npm start. El chat quedó disponible en http://localhost:3000. En el campo de mensaje se envió el script del enunciado:

<script>alert('Inyección de script');</script>

El navegador mostró el cuadro de alerta, lo que confirma que la aplicación original es vulnerable a la inyección de scripts. El análisis del código mostró tres causas:

  • El frontend inserta el mensaje con $('<li>').html(...) de jQuery, que interpreta el texto como HTML y ejecuta las etiquetas <script>.
  • validateMessage no escapaba nada: devolvía el texto recibido tal cual, también el nombre de usuario y el color.
  • Las funciones is_valid_url_image e is_valid_yt_video usaban una variable inexistente (phone), por lo que lanzaban un error y nunca reconocían imágenes ni videos.

3. URLs de imágenes y videos, y nueva validación en una-lib (pasos 4 y 5)

Las correcciones se hicieron en la carpeta despues/. El método validarMensaje de una-lib (alias en español de validateMessage) ahora recibe el mensaje JSON del cliente y devuelve un objeto seguro para mostrar, con un campo tipo que indica si es texto, imagen o video.

Reglas de validación

EntradaTratamiento
Texto normal o con HTMLSe escapan & < > " ' ` /. El script se muestra como texto y no se ejecuta.
URL de imagenSolo http/https, analizada con new URL(), con extensión jpg, jpeg, png, gif, bmp o webp y sin comillas, espacios ni < >. Se convierte en <img> con la URL escapada.
URL de videoArchivos mp4, webm, ogg → <video controls>. YouTube (youtube.com/watch, youtu.be, /embed/) con un id válido de 11 caracteres → <iframe>.
URL no permitidajavascript:, data:, ftp:, dominios falsos de YouTube o extensiones no permitidas se tratan como texto escapado.
Nombre de usuarioSe escapa y se limita a 50 caracteres.
ColorSolo se acepta el formato hexadecimal #RRGGBB; si no, se usa #000000.
JSON inválido o vacíoSe devuelve el contenido escapado o un mensaje vacío.

Fragmento de validarMensaje (despues/libs/unalib.js)

var texto = typeof obj.mensaje === 'string' ? obj.mensaje.trim() : '';

if (this.is_valid_url_image(texto)) {
  result.tipo = 'imagen';
  result.mensaje = this.getImageTag(texto);      // <img src="URL escapada">
}
else if (this.is_valid_url_video(texto)) {
  result.tipo = 'video';
  result.mensaje = this.getVideoTag(texto);      // <video src="..." controls>
}
else if (this.is_valid_yt_video(texto)) {
  result.tipo = 'video';
  result.mensaje = this.getEmbeddedCode(texto);  // <iframe> de YouTube
}
else {
  result.mensaje = this.escapeHtml(texto);       // texto seguro
}

Cambios en el backend y el frontend

  • server.js: cada mensaje del evento Evento-Mensaje-Server pasa por validation.validarMensaje(msg) antes de reenviarse. El servidor se exporta para poder probarlo, y solo escucha el puerto al ejecutar npm start.
  • index.html: el nombre se inserta en su propio elemento, el color se aplica con .css() después de validarlo y el contenido del mensaje, ya saneado por una-lib, se muestra como texto, imagen o reproductor de video.
Resultado: con la versión corregida, el mismo script del paso 2 aparece como texto literal en el chat y no se abre ninguna alerta. Las URLs de imágenes y videos se muestran directamente en la conversación.

4. Pruebas unitarias (pasos 6 a 8)

Primero se ejecutaron las 5 pruebas existentes del proyecto (Mocha), que pasaron. Luego las pruebas se migraron a Jest, la misma herramienta que se usa en las pruebas de integración. Se ampliaron a 58 pruebas en despues/tests/unit/unalib.test.js, agrupadas en:

  • Validación de URLs de imágenes: URLs válidas (jpg, png, jpeg con parámetros, webp, bmp) y rechazo de páginas HTML, dobles extensiones, ftp:, javascript:, data:, URLs con comillas o espacios y valores no textuales. También se verifica que la etiqueta <img> generada no tenga manejadores de eventos.
  • Validación de URLs de videos: mp4, webm y ogg aceptados; avi, dobles extensiones y URLs con código rechazados. YouTube en sus formatos válidos, y rechazo de ids inválidos, dominios falsos y Vimeo. También se verifica que se genere el reproductor <video controls> o el <iframe>.
  • Prevención de inyección de scripts: el script del paso 2 y cargas como <img onerror>, <svg onload>, <iframe src="javascript:">, <a href="javascript:"> y <body onload>. También el nombre de usuario malicioso, el color inválido, el JSON inválido y las entradas vacías.

Comando: npm test (ejecuta jest tests/unit; la carpeta tests/e2e está en testPathIgnorePatterns).

5. Pruebas de integración (paso 9)

El chat no envía los mensajes por una ruta HTTP sino por Socket.IO, con el evento Evento-Mensaje-Server. Por eso, como indica el enunciado, se instaló socket.io-client además de jest y supertest:

npm install --save-dev jest supertest socket.io-client

El archivo despues/tests/integration/chat.test.js levanta el servidor real en un puerto libre y se conecta como lo haría el navegador. Con jest.spyOn se comprueba que el backend llama realmente a validarMensaje de una-lib. Al terminar, se cierran los clientes y el servidor (io.close()). Casos cubiertos:

CasoQué se verifica
GET / con SupertestCódigo 200, tipo text/html y la página del chat.
URL de imagen válidaEl backend la acepta: tipo: "imagen" y etiqueta <img>; validarMensaje se llamó una vez.
URL de video válida (mp4)El backend la acepta: tipo: "video" y reproductor <video controls>.
Video de YouTubeSe devuelve el <iframe> con el id correcto.
Script del paso 2Se devuelve saneado como texto, sin <script.
URL no permitida (javascript:)No se convierte en etiqueta; queda como texto sin < >.
Nombre de usuario con HTMLEl nombre se devuelve escapado.

Comando: npx jest tests/integration --runInBand --env=node

6. Pruebas end-to-end con Playwright (paso 10)

Se configuró Playwright en despues/ con JavaScript, la carpeta tests/e2e y el navegador Chromium. En playwright.config.js se definió testDir: './tests/e2e' y use.baseURL: 'http://localhost:3000', que es la URL real del frontend. La opción webServer reutiliza el servidor si ya está iniciado con npm start. Las pruebas corren con un solo worker porque el chat reenvía cada mensaje a todos los clientes conectados.

El archivo despues/tests/e2e/chat.spec.js usa page.goto, getByRole, fill, click y expect para tres casos:

  • Imagen: envía una URL de Wikimedia y verifica que el <img> es visible y que terminó de cargar (complete y naturalWidth > 0).
  • Video: envía un mp4 de MDN y verifica que aparece el reproductor con controles y que cargó el contenido (readyState ≥ 1 y duración mayor que 0).
  • Script del paso 2: registra page.on("dialog") antes del envío. La prueba falla si aparece cualquier alerta. Además comprueba que el mensaje se muestra como texto literal y que no se insertó ningún <script>.

Como control, la prueba del script se ejecutó también contra la versión original (antes/) y falló, como se esperaba. Así se confirma que la prueba detecta la vulnerabilidad y que pasa solo con la corrección.

Comando: npx playwright test --project=chromium --headed

7. Resumen de resultados y conclusiones

SuiteHerramientasComandoResultado
UnitariasJestnpm test58 / 58 aprobadas
IntegraciónJest, Supertest, socket.io-clientnpm run test:integration7 / 7 aprobadas
End-to-endPlaywright (Chromium)npm run test:e2e3 / 3 aprobadas
  • La aplicación original ejecutaba cualquier script enviado por un usuario. Como el chat reenvía los mensajes a todos los conectados, un atacante podía ejecutar código en el navegador de todos los demás usuarios (XSS almacenado y distribuido).
  • La corrección principal es validar en el servidor: todo el texto se escapa y solo se convierten en HTML las URLs que cumplen reglas estrictas (protocolo, extensión y caracteres permitidos). El HTML de imágenes y videos lo genera la propia librería, nunca el usuario.
  • Las tres suites se complementan. Las unitarias prueban la lógica de una-lib. Las de integración confirman que el backend usa esa lógica en el evento real de Socket.IO. Las end-to-end demuestran en un navegador real que el usuario ve las imágenes y videos y que el script ya no se ejecuta.
